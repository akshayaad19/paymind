PayMind

A scalable tool-calling agent for PayPal

Users ask in plain English. The agent finds the right PayPal API among many, fills in the parameters, lets code check the call, asks the user before anything changes, runs it, and shows what really happened. Every step is traced in LangSmith.

Akshayaa D · github.com/akshayaad19/paymind · September 2026
112PayPal APIs as searchable tool cards, from the Postman collection
100%right tool in the top 5 at 1,012 tools (with 900 look-alike distractors)
~20 msper tool search (hybrid BM25 + dense, RRF)
234automated tests, run without any LLM
The idea in one line. The model never sees every tool: each message runs a role-filtered hybrid search and offers only the top 5 tools plus a few built-ins (including the RAG pipeline tool and the System Search tool). The prompt stays the same size whether there are 100 or 10,000 tools, and everything with a right answer (permissions, amounts, IDs, confirmation) is decided by code, not by the model.

5 Agent structure

One ReAct agent (reason → act → observe, repeated) as a LangGraph state machine. The loop runs as many rounds as the question needs (0 for "what can you do?", 3 for "refund Rahul's disputed payment"), capped at 8.

NodeLLM?Job
search_toolsNoPicks this message's tools (section 6). Short follow-ups ("refund the first one") are searched with the previous message.
agentYesReads the conversation, tool results and errors; calls tools (chaining dependent ones, e.g. list → details → refund) or answers.
gateNoChecks every proposed call (section 9); for writes, pauses with interrupt(). Changes no data, so a resumed run never repeats an action.
toolsNoRuns approved calls, filters list results to the caller's own records, writes the audit log, records what really ran.
Why one agent, not several? Tool search already does the routing a supervisor would do, for one LLM call fewer per message, and safety stays in deterministic code rather than a second "validator" LLM. Domain sub-agents can be added as LangGraph sub-graphs if one prompt can no longer hold the rules (section 12).

6 Tool selection and routing

Figure 3. Retrieval-first routing. Each card is indexed from its name, category, description and four example questions.

Why this scales

  • The prompt holds 5 tools whatever the catalogue size: cost and accuracy don't degrade as APIs are added.
  • Adding an API = add a card and re-index. No prompt changes, no code changes.
  • Permissions are enforced in the search itself: a customer's model never sees a refund tool.
  • find_tools lets the model recover if the first 5 miss.
  • Measured at 1,012 tools in section 11.

7 RAG pipeline tool and System Search tool

System Search answers questions about the assistant itself: mode=capabilities searches the tool index (role-filtered, synthetic test tools hidden) for "what can you do with invoices?", and mode=activity reads the user's own audit log for "what's the status of my last request?". Where policy involves money it is also enforced in code: e.g. in-store purchases can get at most 50% back, whatever the model says.

8 State and memory

AgentState fieldHolds
messagesThe conversation (appended)
offeredTools the model may call
seenText used to check IDs are real
stepsRounds so far (max 8)
decisionsThe gate's verdict per call
actionsWhat really ran → receipt
  • One shared state; each node returns only the fields it changes (messages is appended, the rest replaced).
  • The checkpointer saves it after every node, per user_id__session: chat memory for follow-ups, and a paused run resumes exactly where it stopped after the user's Yes.
  • Identity: the JWT only says who you are; the role is read from the database on each request, and a token version lets logout revoke every copy.
  • Business data: PayPal is the source of truth; the app database keeps only what PayPal has no concept of.

10 Observability: what the traces show

Every chat message is one LangSmith trace named paymind_chat. LangGraph traces each node automatically; four custom spans (@traceable) record our own decisions. Filter by the tag role:customer / role:accountant, or by user and session in metadata.

Figure 5. One trace. Green spans are our custom spans: the code decisions that make the system safe, and the first place to look when something goes wrong.
SymptomWhere the trace shows the cause
Wrong or no tool usedtool_search: was it in the top 5? If yes, the LLM span shows what it chose instead.
"It said done but nothing happened"validate (blocked / invalid?) and whether a paypal_api span exists; the receipt shows the same.
Slow answerPer-span latency: nearly always the LLM (or a fallback after a timeout); PayPal calls take milliseconds.
Access questionpaypal_api records the caller, the tool's allowed roles and role_allowed.

For users, the in-app audit log keeps every action (who, what, when, result); developer detail stays in LangSmith.

11 Scalability: measured

Does tool search still find the right tool at 1,000+ tools? 42 hand-written questions (not from the tool cards) were searched over the 112 real tools, then with 400 and 900 synthetic tools from 25 look-alike services (other payment, billing, CRM, accounting, shipping and support APIs) that reuse PayPal's vocabulary: "refund a charge", "list invoices", "respond to dispute".

ToolsSearchTop-5Top-1ms
112BM2588%60%10
112Dense95%83%10
112Hybrid100%79%21
512BM2579%52%9
512Dense95%83%10
512Hybrid100%76%20
1,012BM2576%52%9
1,012Dense95%79%13
1,012Hybrid100%71%23
Reading. Keyword search alone degrades as look-alikes are added (88% → 76%); dense holds at 95%; the hybrid keeps the right tool among what the model sees every time, at about 20 ms. Top-1 slips from 79% to 71%, which is why the model is shown 5 candidates and picks with their descriptions. Limits: 42 questions, template-generated distractors, in-memory Qdrant. Reproduce: python -m paymind.retrieval.eval_tools.

12 Scaling to thousands of customers

Today everything runs as one process with SQLite. For thousands of customers the agent design stays the same; the pieces around it become shared services, so any number of stateless API instances can serve any request.

Figure 6. Production architecture. Red: the cache and its invalidation path. The agent graph, tools and rules are unchanged; only where state lives changes.
PressureAnswer
More users at onceStateless API instances behind a load balancer; state in Postgres (PostgresSaver), so any instance resumes any chat or confirmation. SSE keeps one connection per answer.
Repeated lookupsRedis: the user row (role, token version) with a short TTL and delete-on-change; What's new per user; tool-search results per role and query. Cache-aside, always falling back to Postgres.
LLM limits and costAn LLM gateway with per-user rate limits (Redis counters), the existing model fallback chain, and cost caps. One LLM call per round, with a 5-tool prompt.
Slow workReading handwritten POs and sending notifications move to a Redis queue and workers, so chat stays fast.
More tools (10,000+)Same retrieval-first design; shard the Qdrant collection, add a service/category pre-filter and a cross-encoder reranker on the top 20 tools to lift top-1; domain sub-agents only if one prompt can't hold the rules.
Large audit logsPostgres partitioned by month; LangSmith traces sampled (all errors and writes, a share of reads).

14 Limitations and next steps

  • PayPal is a mock server with real request/response shapes; the next step is the PayPal sandbox with OAuth.
  • The scaling eval is small (42 questions); grow it from real traces, run it in CI, and add the tool reranker to lift top-1.
  • Measure end-to-end task success and tool-choice accuracy with the LLM, not only retrieval.
  • Production hardening from section 12: Postgres, Redis, HTTPS, secrets manager, rate limits, object storage.
